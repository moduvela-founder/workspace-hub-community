# DEMO 验证与产品化推进约定

适用于产品、工具、框架、软件、硬件、AI 能力和单个功能的开发。新探索和新功能优先得到最小可验证结果，再按交付需要做产品化；已上线功能的修复和维护继续满足既有承诺。本规范不替代目标项目的需求、硬件边界、审批与验收门，也不自动改写旧项目。

## 两个模式与本轮终点

| 模式 | 本轮关注 | 可以采用的方式 | 验收含义 |
| --- | --- | --- | --- |
| DEMO 验证 | 用最短可靠路径验证一个明确能力或关键假设 | 脚本、CLI、固定实验参数、人工步骤、有限场景；优先复用已有实现 | 约定条件下的功能与结果得到验证，并保留必要证据和已知限制 |
| 产品化 | 使已验证能力满足明确的使用和交付要求 | 按实际受众补齐接口、配置、错误处理、部署、文档、维护和必要回归 | 达到本轮已约定的交付标准；涉及量产时再采用对应量产要求 |

**当前模式和本轮终点分别约定。** 模式说明现在如何投入，终点决定这次任务包含多少工作：

- “先跑通、试一下、验证能否实现”默认止于 DEMO 验收；达标后汇报结果与限制，不自动扩成产品化任务。
- 明确要求“完成交付、上线、发布”的任务，先验证最小功能闭环，再继续已有授权范围内的必要产品化。已约定的阶段切换不逐步重复询问；发布、设备等动作仍遵守其原有门禁。
- 用户已明确产品化或既有生产维护任务时，按原承诺推进。可以先做最小复现或验证，但不强制另做演示系统，也不降低现有功能质量。

DEMO、产品化与 `stage` 的设计/实现/验证是不同维度；资产类型 `product` 也不代表已经产品化。同一项目的功能 A 可以在 DEMO，功能 B 可以在产品化。模式归属于当前任务或里程碑，不能给整个仓库永久贴 DEMO 标签。

## 开始前形成短约定

新项目、独立新功能或目标发生实质变化时，先读拥有项目的规则与直接相关来源。在已有状态或任务计划中用几行说明下列内容，再推进实现：

1. **对象与目标**：本轮只解决什么问题、验证什么能力；多个目标先排出一条主线。
2. **当前模式与本轮终点**：推荐 DEMO 或产品化；本轮到 DEMO 验收，还是包含随后哪些交付工作。
3. **验收条件**：输入、操作条件、可观察结果与必要证据；避免使用“完善”“稳定可用”等无边界词。硬件区分仿真、台架和实机结果。
4. **最小实现与必要边界**：选定路线与复用/复现入口；有可用参考时说明关键组合、必要适配及选择依据；允许的临时方式，以及本次必须保留的操作、数据和设备约束。
5. **暂缓项与后续产品化**：哪些已知问题暂不阻塞，哪些交付事项只有到产品化才处理；尚未确定时明确待定。

信息已明确时直接形成约定并在已有授权内执行，不把它变成每轮问卷或新增审批。仅当缺失选择会改变范围、外部效果、风险边界或验收结论时，集中澄清关键选择；澄清期间可继续独立工作。推荐与待确认内容不得写成用户已批准要求。只读分析时约定留在回复里，不写项目文件。

小任务可用一两句话覆盖这些内容，不要求填写完整表格。新建项目的模板保留待确认项，不能仅因模板推荐 DEMO 就宣称模式或目标已经获确认。

## 按目标选择实现路线

DEMO 以约定的能力、结果与验收条件为目标，修好旧实现只是候选路线。任务明确要求修复指定实现或定位根因时，仍须满足该要求并保留对应证据；已上线功能和生产维护继续满足既有承诺。

开始实现或重整主线时，先查看已有官方示例、社区案例或内部成功版本等直接相关来源，必要时围绕当前目标定向查找，选择最小路线。发现前提匹配且可用的成功参考时，优先以其关键完整组合作为基线复现；仅做使其在本项目运行所必需的适配，按约定条件验证基线结果后再逐项引入其余已授权改动，并完成本轮验收，避免先拆取零散参数而持续修补自己的实现。

关键完整组合指支撑成功结果的实现、依赖/模型/固件版本、配置参数、输入、硬件与操作条件等相关链路，按项目取实际相关项，不要求照搬全部 UI、服务或无关功能。采用前核对目标与前提是否匹配、条件是否可用、许可和操作边界是否允许，保留来源与必要差异。参考成功不能代替本项目验收，硬件、数据等差异仍按实际验证范围记录。

没有匹配可用的参考、条件或许可不允许、复现成本不合理，或已有依据表明当前实现更直接时，继续最小实现或可区分原因的实验，并简记选择依据。搜索与复现服务于当前目标，不强制每项任务联网搜索、穷尽方案或新增研究阶段与门禁；路径切换仍遵守现有范围、授权和硬件边界。

## DEMO 的执行方式

- 先跑通“输入 → 核心能力 → 可观察结果 → 必要记录”的最小闭环。已有 CLI、脚本、API 足够时优先使用，不为开发操作默认增加网页、仪表盘或新服务。
- 可以固定本次实验参数、手动启动和部署、限定设备与场景；在已有入口附近记录使用方式和限制。DEMO 实现允许以后被替换，不预先承担未来扩展要求。
- 一次推进一个可验证步骤。选择最能减少当前不确定性的下一项实验，不把全部潜在问题排成必做前置工作。
- 实验所需的停止、限幅、独占设备、秘密与数据保全等边界按具体操作确定，优先复用现有机制。临时实现不豁免必要边界；基本防护也不自动成为建设完整安全平台的授权。
- 测试围绕本轮行为和改动影响，遵守已有必需检查。日志足以判断本次结果即可；不为 DEMO 默认建立全量监控、兼容矩阵、发布体系或全面重构。
- 验收通过后保留复现入口、关键参数/版本、结果证据和限制。只覆盖一个条件的成功不能外推其他设备、场景或量产可用性。

DEMO 可以按功能拆成连续小闭环，每个功能验证后再做其必要产品化；不要求整个产品全部 DEMO 完成才整理，也不要求每个功能维护两套代码、分支、仓库或独立项目卡。

本轮涉及界面设计、实现或审查时，按[界面信息与视口验收](ui-delivery.md)约定信息、视口与画面证据，DEMO 与产品化均适用。已有 UI 不使纯后端、脚本或文档任务自动读取界面规范，也不为没有 UI 需求的任务新建界面。

## 新问题如何处理

遇到 BUG 或其他问题，先判断它是否仍属于达到当前验收目标的选定最小路线，再决定修复、复用或替换。对会明显扩大本轮工作的提议，先说明它影响哪个当前验收项，以及为什么现有条件或更小改动不足：

| 情况 | 本轮处理 |
| --- | --- |
| 阻塞选定路线完成或判断当前目标，例如命令方向错误、关键记录缺失 | 采用最小必要的修复、复用或替换，然后回到主线 |
| 本次操作存在已观察或明确可预见的人员、设备、数据损害机制 | 说明具体风险，采用最小必要措施；无法建立可行边界时暂停相关动作，继续可独立工作 |
| 尚无证据的缺陷猜测或原因不明 | 优先选择低成本、可区分原因的验证，不先设计通用防护体系 |
| 易用性、泛化、界面、未来兼容、产线或正式发布需求，当前验收不依赖 | 记入已有待办，留到对应产品化范围，不升级为当前阻塞 |

同一问题可能因任务不同而归入不同情况；不得只凭“安全”“最佳实践”或“以后会用到”无限扩项，也不能只因标记 DEMO 就撤销原有门禁。有冲突时说明约束来源、影响与最小可行选择，按现有授权解决或澄清，不静默覆盖项目要求。

问题记录写入已有状态、问题清单或计划，按需要采用下面的短格式，不为每个问题新建文件或强制编号：

```text
问题：现象及范围（已有问题 ID 可保留）
依据：已确认 / 待验证；复现或证据入口
影响：阻塞哪个当前验收项 / 产品化待办 / 暂不阻塞 / 待判断
处理与关闭：最小下一步；通过条件与关闭证据
```

小问题可合成一行。影响待判断时先安排可区分原因的验证；明确可预见的损害风险仍按上表建立操作边界。人工待办与本轮 gate 的区别遵循[文档契约](document-contract.md#manual_stepsmd)，在当前执行约定中引用实际适用的门禁，不把所有未勾选事项都提升为当前阻塞。

## 验收、转入产品化与停止

DEMO 达标时核对约定的结果与证据，明确通过范围及未解决问题。若需要人工体验、现场测试或正式批准，保留该验收点；无需人工的可测验收由实施者在授权内完成。编译、页面渲染或模拟通过不替代对应功能/实机验收。

在既有状态/计划中留下复现入口、证据、限制与接下来必要事项即可，不另产阶段报告，也不额外设置一律等待人工确认的步骤。

本轮终点只到 DEMO 时，在这里收口并给出下一阶段建议。本轮已包含产品化时，沿用已约定范围继续，补齐满足实际交付所必需的事项；新增大范围重构、框架提取、全新 UI、量产设计等另按范围变更处理。产品化也有完成标准，不以“所有 BUG 清零”为终点；没有必要就不重写已可用实现。对外部署、发布、提交推送和设备动作分别沿用已有授权，不由模式切换自动授予。

验证未通过时，记录失败条件、证据、当前假设和下一项最小实验，不标记完成。若已约定实验次数、时间或硬件操作边界，到界后按约定收口；继续会明显扩大范围时说明选择。没有预设预算时不凭空设置停止次数，也不因发现旁支问题进入无界整改。

发现更匹配的可用成功参考，或连续尝试不再产生可区分原因的新证据时，归纳已排除项、当前卡点与可选的最小路径，重新比较路线并调整实验或实现方法；不以重复同类实验代替推进。需要用户选择会改变范围的路径时再集中澄清。

必要的产品化收尾与用户显式调用的会话结项整理分别处理；本流程不自动触发 `$session-closeout`、压缩或归档会话。

## 在现有文档中接入

- 当前约定保存在拥有项目的 STATUS 正文；详细需求或功能计划已有权威文档时，STATUS 只留当前重点与链接。格式见[文档契约](document-contract.md#当前执行约定)。
- AGENTS 只保留读取触发和本项目稳定约束，详细共用规则指向本页。同一会话在约定未变时复用，不每次重新读取和确认。
- 多功能并行时，在已有计划中分别表达模式与终点，由一个写入者汇总 STATUS；不为每个功能增加标准四文件或重复状态。
- 暂缓事项留在已有待办/计划中；MANUAL_STEPS 只放确需人工、现场或外部条件的事项，不塞入所有技术债。
- 旧项目在获授权的整理中，将当前 DEMO 阻塞与后续交付事项分清。原需求、验收门、证据和历史状态保留；不批量改写、不重新认证历史成果、不借整理启动构建、硬件或发布。
- 当前约定为文档工作方式：没有新增 YAML 状态枚举、网页模式切换、任务自动调度或规则强制拦截。已有全局/项目指令的加载由客户端管理，不能以修改文件推断运行中的会话已经采纳。

## 复制给新项目或当前会话

本页在 Hub 资料成员中使用 `workspace-hub:workspace-hub#hub/delivery-workflow`；网页复制成员引用会附实际索引库位置。下面的提示词与该引用一起粘贴即可，不需要复制整篇规范。先解析引用并读原文，保留目标项目自己的规则。

**新项目或新功能**：

```text
请按这个 Workspace Hub 引用中的 DEMO/产品化约定推进当前需求。
结合本项目规则，先给出最小主线、验收条件、允许简化和暂缓项，推荐当前模式与本轮终点。
按约定能力和结果选路；有匹配可用的成功参考时优先复现关键完整组合，必要适配并验证基线后，再引入其余已授权改动并完成本轮验收。
新探索/功能优先 DEMO；若本轮已要求完整交付，在功能验收后继续已授权的必要产品化。
信息足够时直接推进；仅澄清会改变范围、外部效果或安全的关键选择。
在本次获授权的实施中，把执行约定合并到已有状态/计划，不另建一套管理文档。
```

**旧项目或长会话先重整约定**：

```text
请按这个 Workspace Hub 引用重新审视当前任务，先只读分析，不实施或操作设备。
区分当前功能目标、DEMO 实际阻塞与后续产品化事项，保留已有需求、验收门和证据。
按当前目标重新比较修复、复用或替换路线；有匹配可用的成功参考时，评估其关键完整组合的复现与必要适配，不默认把修好旧实现当作目标。
给出当前模式、本轮终点、最小下一步、完成标准与可暂缓事项，并指出与旧约定的冲突。
不要把历史提议当当前要求，也不要自动取消旧门禁；待我确认调整范围后再更新已有文档和实施。
```
