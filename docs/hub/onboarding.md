# 登记与整理流程

## 首次整理旧项目

1. 确定产品/工具/框架/流程的主目录，读取其及祖先 AGENTS.md；只读直接相关 README、进度、协议、验证入口。不要读取全量代码、原始聊天、备份或凭据来补摘要。
2. 确定资产类型、实际目标、来源与未知。识别关联仓库、主 checkout、worktree、副本；保存原路径，不按 Git 数量或文件数量计算项目数量。需要重整开发主线时，按[DEMO/产品化约定](delivery-workflow.md)区分当前功能阻塞与后续交付事项；没有依据时不把旧项目降级为 DEMO，也不取消旧验收门。
3. 映射已有文档。在已授权的整理范围内补足缺失入口，或向原 AGENTS 合并[共享规则短入口](project-rules.md)；保留已有内容和产品审批门。工具/流程只登记文档也可，不强迫每个依赖仓库加入文件。
4. 写简短目录记录及来源日期。成熟度要有证据；历史验证标明日期和范围，不代表当前设备在线。矛盾先标待确认，保留来源。
5. 校验目录 ID、关系和路径。批量整理先按登记清单小批推进，尊重每个项目的文件/批准门，不能把扫描变成自动改写所有项目。

来源不完整时保留空路径与说明，登记范围不等于全量盘点；意向项目不因进入目录就成为依赖。

旧输出目录治理只在获授权的范围内进行：先按[存储与输出约定](storage-and-outputs.md)确认所属仓库、实际工作区、owner、内容类别和历史路径引用；保留混合证据及未提交源码。首次登记或规则接入不授权搬迁/删除已有目录，也不因提交已合并而判定 worktree 可退役；不为统一命名批量覆盖已有规则或迁移旧布局。

## 新建目录

使用 CLI `init` 先预览，仅在授权的新项目主目录写入不存在的文件。已有 AGENTS、README 和产品参数不覆盖。初始化没有完成 catalog 登记，随后显式加入 `catalog/assets.json` 并校验。不要为 worktree 再初始化一份产品状态。

模板只提供当前执行约定的填写入口。开始实际开发时结合需求推荐模式与本轮终点，新探索/功能优先 DEMO；初始化不代表这些选择已经确认。具体方式与可复制提示词见[推进约定](delivery-workflow.md)。

旧项目若已有自定义进度/人工步骤文档，先映射它们，再有针对性地补入口；不要直接用 `init --apply`，因为它只判断四个标准文件是否存在，不识别替代事实来源，仍会补出 STATUS/MANUAL_STEPS。此类项目保留原文档并手工合并缺失入口即可。

```bash
# 在实际 Hub 根执行；替换演示路径为已授权且位于允许根内的主目录。
node scripts/hub.mjs init \
  --path /absolute/path/to/new-product --id new-product --title '新产品' --kind product
```

默认预览；属于已授权的实施任务时，同一命令加 `--apply`。登记后执行 `node scripts/hub.mjs validate`。上例路径仅演示，不是预先登记的产品。初始化不覆盖已有 AGENTS；旧项目的接入需有针对性地合并，不能用 init 伪装规则自动升级。

## 持续更新

实施者按[文档契约](document-contract.md)维护改变的状态；扫描器读取登记入口并报告变化、缺失、过期，不写回项目文件。人工结果只有获得依据才更新。共享状态文件避免多写入者竞争；关联仓库变动不能直接推进全部产品阶段。

## 通用能力与发布流程

工具卡保存用途、入口、环境前提、验证范围与日期。使用前检查目标项目接入和当前运行状态。框架候选保存原实现、接口和适用条件；先登记，再在有明确需求时提取共享组件。

GitHub/内网 GitLab、TOS、DEB/APT 只登记已有 runbook 和共享流程入口，不复制凭据或重写其批准边界。产品包名、平台、版本、目标发布地址、构建参数和验收仍归产品。打开目录卡不构成发布、推送或硬件操作授权。
